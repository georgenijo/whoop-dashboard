Executive Summary

The codebase scores A (91.7/100) across 209 files — no critical defects, zero import cycles, and average cyclomatic complexity of 4.2. That headline is accurate but incomplete. Underneath it, coupling collapsed 19 points (100 → 81) between Apr 22 and May 13, the single largest metric movement in the observation window and the only reading that crossed the 5-point inflection threshold. This happened for a legitimate reason — Phases A–D wired user_id isolation across every domain table, added forUser wrappers, HMAC OAuth state, encrypted vault helpers, and webhook-to-user mapping — but the structural cost is now visible: auth.ts has 31 fan-in callers, connection.ts has 17, and both have become de facto chokepoints that every new route touches by default.

Trajectory is mixed. Complexity is improving (+3 pts net), cohesion hit a perfect 100 after the db.ts domain-module split, and TDG is marginally up. Duplication is the one dimension actively trending the wrong direction: it fell 5 points from baseline (96 → 91) and has not recovered, with 77 clone groups and 999 duplicate lines spread across chart cards, the three LogsTable variants, and self-clones inside connection.ts, logs.ts, and upsert.ts. Self-clones — where the same block is duplicated within a single file — are the most urgent duplication risk because both copies must be updated simultaneously on the next edit.

The three concrete risks are: (1) auth.ts as a single structural chokepoint — 31 dependents, highest betweenness in the graph, and a breaking change here disconnects more module pairs than any other file; (2) the coach subsystem god-route — api/chat/route.ts scores 0.985 on the hotspot index (18 commits, 98th-percentile complexity) while still owning SSE transport, agentic loop orchestration, tool dispatch, and persistence in one handler; (3) connection.ts absorbing every schema change — 24 commits, the single D-grade file in the repo (TDG 62.7), cyclomatic complexity 46, and 16.7% internal duplication.

The path forward is three targeted refactors, not a broad cleanup. Split auth.ts into session/guard/identity submodules to reduce its blast radius. Finish the coach route split that PR #675e0d4 started — push loop orchestration into loop.ts and persistence into persistence.ts, leaving route.ts as pure SSE transport. Extract a migration runner from connection.ts so schema changes stop touching live connection code. Beyond those three, the highest-value quick wins are extracting a LogsTable base component (eliminates ~150 lines), a shared useChartDateRange() hook (eliminates ~74 lines), and a signAppleJWT() helper from the auth/push duplication (eliminates ~18 lines but closes a security-relevant divergence risk).

Architectural Smells

Structural problems that make the codebase harder to change safely

No cyclic dependencies detected — modules can be tested and deployed independently without circular import concerns. Two high-severity hub smells dominate the picture.

streamlit/whoop/db.py is the most extreme hub in the codebase: fan-in of 60 with zero fan-out. Every Streamlit page and analytics module imports it directly. Because it has no outbound dependencies, it is maximally stable, but that stability is a trap — any schema change, query refactor, or connection behavior change requires touching (or re-testing) 60 callsites. Action: split into domain-scoped query modules (e.g. db_sleep.py, db_recovery.py, db_workouts.py) and introduce a thin shared connection helper. Callers import only what they need.

apps/web/src/lib/auth.ts is the web app's equivalent: fan-in of 31, fan-out of 4, instability 0.11. Nearly every API route and several components depend on it directly. It carries authentication session logic, cookie handling, and user resolution — three distinct concerns. Because everything flows through it, it cannot be mocked cheaply in tests and any breakage propagates immediately to 31 modules. Action: extract a narrow getCurrentUser() boundary (pure session token → user ID resolution) into its own module; push cookie manipulation into lib/auth/cookies.ts (already exists, fan-in 6); leave only the orchestration glue in auth.ts. This reduces the blast radius of auth changes.

apps/web/src/lib/db/connection.ts (fan-in 17, fan-out 0) is a silent secondary hub — not flagged because it falls below the hub threshold of 20, but it is the single database connection provider for all 17 db/* modules. It is appropriately stable (instability 0.0) and focused, so no split is needed, but it should be treated as a frozen interface: no logic beyond connection setup should ever be added here.

apps/web/src/lib/db/scoped.ts (fan-in 7, instability 0.125) is a near-hub that wraps scoped DB access. Seven modules depend on it. Low risk now but watch the fan-in — if it crosses ~12 it becomes a coupling bottleneck similar to connection.ts.

coach subsystem instability: lib/coach/persistence.ts (instability 0.83, fan-out 5) and lib/coach/loop.ts (instability 0.75, fan-out 3) both carry critical AI-loop logic while depending heavily on other modules and being depended on by very few. High instability in load-bearing logic means these modules are likely to break or need changes frequently. Action: stabilize persistence.ts by extracting its storage interface — callers should depend on a stable interface type, not the concrete persistence module.

Page-level fan-out is high but expected: sleep/page.tsx (fan-out 26), workouts/page.tsx (fan-out 8), recovery/page.tsx (fan-out 15), page.tsx (fan-out 11) are all leaf nodes with instability 1.0. This is normal for Next.js page components — they aggregate many display modules. No action needed unless a page component starts containing business logic.

Summary of priority actions: (1) Split streamlit/whoop/db.py into domain query modules — highest leverage, 60 dependents. (2) Extract getCurrentUser() from auth.ts to reduce its 31-dependent blast radius. (3) Introduce a storage interface in coach/persistence.ts to stabilize the AI loop boundary.

Temporal Coupling

Files that frequently change together - reveals hidden dependencies not in the import graph

Three high-signal findings stand out. First, TopBar.tsx ↔ db.ts (strength 0.75) is the strongest non-trivial coupling in the codebase: a UI chrome component co-changes with the database layer on 6 of 8 commits. There is no plausible import relationship here — this is a shared assumption about data shape or auth state leaking into presentation. Extract whatever DB concern TopBar is reacting to (likely session/user or nav counts) into a dedicated query hook or server component so the chrome layer stops tracking schema changes. Second, the whoop/ module cluster (client.ts ↔ token.ts, client.ts ↔ upsert.ts, sync.ts ↔ client.ts, all at 0.67) forms a tight co-change group that spans auth, HTTP, and persistence in lockstep. These three files move together because they share assumptions about token shape and refresh behavior that are not encoded anywhere — they live in each file's head. Extract a WhoopSession or WhoopConfig struct (token, expiry, userId) passed explicitly, so a token-format change touches one definition instead of rippling across all three. Third, apps/web/src/lib/db/sleep.ts ↔ streamlit/whoop/db.py (strength 0.57) is the sharpest cross-package signal: a TypeScript DB module and a Python Streamlit query file move in sync across 4 commits. They are duplicating the same schema knowledge in two languages with no shared source of truth. Define the sleep record schema once — either as a SQL migration or a shared JSON schema — and have both consumers derive from it. The db/connection.ts file (24 commits, coupled to nearly every module at 0.12–0.37) is a hub rather than a coupling problem, but its breadth confirms it is doing too much: schema initialization, connection pooling, and possibly migration logic are all mixed in one place, which is why everything touches it during any structural change.

Glossary of Terms

▼

Health Score

A weighted composite metric (0-100) measuring overall code quality. Above 80 is good, 60-80 needs attention, below 60 is concerning.

Hotspot

A file that is both complex AND frequently changed. These are the highest-risk areas because they're hard to change safely but get changed often.

Bus Factor

The minimum number of people who would need to leave before critical knowledge is lost. Higher is better; 1 is a serious risk.

Knowledge Silo

A file that only one person has ever touched. If that person leaves, the knowledge goes with them.

Cyclomatic Complexity

The number of independent paths through code. More paths means more test cases needed and more ways things can go wrong.

Cognitive Complexity

How hard code is to understand. Accounts for nesting, breaks in flow, and things that make humans struggle to follow the logic.

LCOM (Cohesion)

How well a class's methods work together. High LCOM means methods don't share data - the class is probably doing too many unrelated things.

CBO (Coupling)

How many other classes a class depends on. High coupling means changes ripple through the codebase - everything is connected to everything.

Churn Rate

How frequently a file changes. High churn indicates instability - the code may be unclear, have bugs, or be undergoing active development.

Self-Admitted Technical Debt (SATD)

Code issues the team has documented (TODO, FIXME, HACK, XXX). These represent known shortcuts that need eventual attention.

Code Clone / Duplicate

Similar code appearing in multiple places. When a bug is fixed in one spot, it may need fixing elsewhere. Candidates for refactoring into shared functions.

Technical Debt Gradient

Per-file quality score (0-100) combining complexity, duplication, coupling, and other factors. Lower scores mean more accumulated debt.

Temporal Coupling

Files that frequently change together in the same commits. High temporal coupling suggests hidden dependencies not visible in the import graph.

Architectural Smell

A structural pattern that violates design principles: cyclic dependencies, hub-like modules, or stable code depending on unstable code.

Instability

Ratio of outgoing to total dependencies. 0 = maximally stable (many things depend on it), 1 = maximally unstable (depends on many things).

PageRank

Importance of a file in the dependency graph. Files with high PageRank are depended on by many other important files.
