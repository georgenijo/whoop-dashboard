Whoop Dashboard — Current Architecture

Personal-use single-tenant deployment as of 2026-05-08

Single user (George), single VM, single SQLite file, single Whoop OAuth token, single Anthropic API key in env.

Single-tenant assumptions

  • user_id=1 bootstrap fallback in requireAuth() when no auth header
  • iOS path uses Apple sub → user_id=2 (cross-device split)
  • Most read queries omit user_id filter — single-user safe, multi-tenant unsafe
  • Public domain gated by Cloudflare Access email allowlist (1 entry)

Single-key surfaces

  • tokens.json at repo root — one Whoop OAuth token for one Whoop account
  • ANTHROPIC_API_KEY in .env — every Coach call billed to George
  • WHOOP_CLIENT_ID/SECRET — one developer app, all sync calls share its rate budget

Sync flow

  • daily_sync.py manual: reads tokens.json → fetches last 7 days from Whoop → upserts to SQLite
  • Token refresh: thread-safe atomic write back to tokens.json
  • 5-min cooldown short-circuit on /api/sync (PR #231)
  • No cron / systemd timer — every sync triggered by hand from Settings or CLI

Coach flow

  • /api/chat agentic loop: Sonnet 4.6 + 5 tools (recovery/sleep/strain/workouts/journal)
  • Caps: 8 tool iterations, 16K output tokens
  • Persistence: chat_threads + chat_messages with blocks JSON column
  • Auto-titles via Haiku 4.5 in Next.js after() hook

Deploy

  • Ubuntu VM · whoop-web.service systemd · port 8501
  • Manual: ssh → git pull → npm ci + build → systemctl restart
  • No CI · no automated tests · no Postgres / replicas

What scales today

  • SQLite WAL handles current load with comfortable headroom
  • Next.js + better-sqlite3 sync access is fine for 1 user's read pattern
  • Anthropic adaptive thinking + 16K cap keeps Coach cost predictable
