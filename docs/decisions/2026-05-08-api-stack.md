# 2026-05-08 — API stack: Hono + Zod + OpenAPI + Scalar

**Status:** decided, not yet implemented
**Tracking issue:** #233
**Owner:** George
**Context window:** Phase 3 just shipped (CF Access JWT, TS-port sync, Xcode Cloud). Discovered `coach-api.georgenijo.com` serves the same UI as `coach.*` — security leak.

## Why this matters

Right now there are two domains pointing at the same Next.js app:

| Domain | Intended purpose | Today |
|---|---|---|
| `coach.georgenijo.com` | Web UI | Gated by Cloudflare Access at the edge. Only George reaches origin. |
| `coach-api.georgenijo.com` | iOS API only (bearer-only, no Access) | Serves the **same** routes as `coach.*` — including the SSR UI pages. |

The split was conceptual: `coach-api.*` was supposed to expose only `/api/*` for the iOS app, since iOS uses SIWA Bearer tokens and can't go through Cloudflare Access. But nginx routes both hostnames to the same Next.js process, with no per-host filtering. Anyone who discovers `coach-api.*` can reach SSR pages without auth.

Per-API-route auth is still enforced (`requireAuth` in `apps/web/src/lib/auth.ts`), but page routes are inconsistent — some used `getBootstrapUser()`, some didn't authenticate at all. We hit one such bug today (PR #224 fixed `/coach/page.tsx`).

The right fix isn't to patch nginx route by route. It's to give the API a real surface — versioned, typed, documented — and let `coach-api.*` serve a docs site, not application UI.

## Decision

Replace per-route Next.js API handlers with **Hono mounted inside Next**. Drive types, runtime validation, and OpenAPI spec generation from **Zod** schemas. Serve the spec via **Scalar** at `coach-api.*/`.

```
[ Next.js page routes ] ─ coach.* (CF Access) ─ user-facing UI
[ Hono handler        ] ─ /api/v1/* (both hosts) ─ JSON API, Zod-validated
[ openapi.json        ] ─ /openapi.json ─ auto-generated from Zod schemas
[ Scalar viewer       ] ─ coach-api.*/ (nginx static) ─ pretty docs site
```

## Why these specific tools

### Hono — router

- Modern, type-safe, minimal. Runs on Node, Bun, Cloudflare Workers, Vercel Edge.
- Mounts in Next.js as a single catch-all route handler — no Next-specific framework lock-in.
- Middleware model is cleaner than Next's per-route boilerplate. `requireAuth` becomes a one-liner.
- MIT licensed, very active, broad ecosystem.

### Zod — schemas

- Already a dependency. Already used in some places (e.g., webhook validation).
- Single source of truth for shape: TypeScript types, runtime validation, and OpenAPI spec all derive from the same `z.object({ ... })`.
- Eliminates the current per-route hand-written validation + interface duplication.

### `@hono/zod-openapi` — spec generation

- Maintained alongside Hono.
- Reads route definitions and Zod schemas → emits OpenAPI 3.1 JSON.
- No drift between code and docs because docs are generated from code.

### Scalar — docs UI

- Modern (2023+), beautiful default theme, dark mode native, search built-in, "Try it" buttons that hit the live API.
- Used officially by Hono, Better Auth, ElysiaJS — natural fit alongside Hono.
- Drop-in: ~10 lines of HTML embeds the viewer reading from `/openapi.json`.
- MIT, self-hosted via nginx — no vendor dependency.

## Why not the alternatives

| Alternative | Why rejected |
|---|---|
| Stay with Next.js API routes + hand-written OpenAPI | Spec drifts from code. Validation is per-route boilerplate. iOS Swift client generation requires a stable spec — drift breaks it. |
| TRPC | Couples to TS clients; iOS app is Swift. OpenAPI is a more universal contract. |
| Swagger UI for docs | Visually dated. Same data, worse experience. |
| Redocly Community | Mature but visually behind Scalar. Three-column layout feels like 2018. |
| Mintlify / ReadMe.com | SaaS dependency + vendor lock-in. Defeats the FOSS goal. |
| OpenAPI Generator only (no router change) | Doesn't fix the per-route auth/validation duplication that's already biting us. Also requires manual annotations everywhere. |
| nginx-only fix (block `coach-api.*` non-/api paths) | Fixes the leak but leaves the API undocumented and the per-route boilerplate intact. Punts the real problem. |

## What this unlocks long-term

1. **Type-safe iOS client.** Generate Swift API client from `openapi.json` via `openapi-generator`. No more hand-written `APIClient.swift` request/response struct duplication.
2. **Versioned API.** Move routes under `/api/v1/*`. Add `/api/v2/*` later without breaking existing iOS builds.
3. **Rate limiting.** Hono middleware — single line per route once foundation exists.
4. **Auth scopes.** When the app moves beyond single-user, per-route scope checks become straightforward.
5. **Public-release readiness.** A documented, versioned, typed API is table stakes for any third-party integration or App Store-public release.

## Migration phases (see issue #233 for the checklist)

1. Mount Hono at `app/api/[[...rest]]/route.ts`. Migrate `/api/dashboard/today` as proof. Same response shape — iOS + web keep working.
2. Migrate the remaining 6 routes. Each gets Zod schemas. `requireAuth` becomes Hono middleware.
3. Add `@hono/zod-openapi`. Spec emits at `/openapi.json`. Versioned `/api/v1/*` with unversioned aliases for one release.
4. nginx split: `coach-api.*/` serves static HTML with embedded Scalar reading `/openapi.json`. `coach-api.*/api/*` proxies to Next as before. `coach-api.*` returns 404 for any non-`/api/*` path that isn't `/openapi.json` or `/`.
5. Optional polish: rate limiting, scopes, generated Swift client.

Total effort: ~3 days across 4 PRs. Migration must complete before the old Next routes are deleted — feature flag or parallel routes during cutover.

## Risks

- **Hono inside Next 16 is uncommon.** Supported via catch-all route handler, but Next 16's specific quirks (see `apps/web/AGENTS.md`) may surface. Mitigation: implement and test phase 1 in a worktree before committing to phase 2.
- **Spec drift during migration.** While some routes are Hono and others are Next, the spec only covers Hono ones. Mitigation: document partial coverage in the README during transition; complete migration before publishing the docs site.
- **Breaking iOS app.** Response shapes must be byte-identical to current. Mitigation: snapshot-test current responses before migration; assert Hono responses match.

## What this does *not* do

- **Multi-user backend.** Still single-user. Auth model unchanged.
- **Public API for third parties.** Docs are for George + future contributors / agents. No API keys, no public consumers.
- **iOS app changes.** iOS continues calling the same paths. Eventually gets a generated client, but not in this migration.
- **Streamlit app.** Legacy, untouched.

## Why write this doc

Anyone (human or agent) coming back to this should understand *why* the API stack changed without re-deriving it from commit messages. The technical change is moderate; the "why" — leaked UI + drift between code and docs + per-route auth boilerplate — is the part that takes context to reconstruct.

If this doc says something the codebase contradicts, trust the codebase and update this doc.
